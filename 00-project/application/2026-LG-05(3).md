# GitHub Projects Portfolio Observatory

## My interpretation of the brief

The project is a web-based monitoring and decision-support application for multiple GitHub Projects. Its purpose is not to replace GitHub Projects, but to provide a unified portfolio-level view of work that may use different fields, names, and workflows. The application must normalise project data, identify items that require attention, retain historical changes, and present the results through personal, team or office, and company-level dashboards.

The main technical challenge is combining authentication, the GitHub Projects v2 GraphQL API, configurable field mapping, scheduled data collection, and role-specific visualisation in one reliable system. The application must also handle permissions, pagination, rate limits, missing fields, and API errors clearly.

## Proposed approach

I would first study the GitHub Projects v2 GraphQL model, authentication scopes, pagination, permissions, and rate limits. I would then define a common work-item model for status, priority, assignee, deadline, and monitoring information. Each connected project would have an explicit mapping configuration so that project-specific field names are not hard-coded.

For the initial implementation, I would use TypeScript and SvelteKit for the web application and evaluate PocketBase or a small database-backed service for profiles, configuration, protected credentials, and historical snapshots. A scheduled GitHub Action or lightweight background task would periodically collect data. Monitoring rules for stale, overdue, blocked, unassigned, and high-priority items would be implemented as independently testable functions. The first complete version would connect at least two projects, normalise their items, store historical changes, and display personal, comparative, and read-only portfolio views.

## Initial plan

6. Create automated tests, evaluate the system with differently configured projects, and document the results.
